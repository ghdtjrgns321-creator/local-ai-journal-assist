마지막 두 행이 방향이 다르다. 앞의 다섯은 "실패로 보였는데 도구·장치 결함이었다"이고, VAE와 부정 표면화는 **"결과를 적어 뒀는데 측정 자체가 성립하지 않았다"**다. 둘의 결말도 갈렸다 — VAE는 데이터가 무효라 재측정해도 얻을 것이 없어 멈췄고, 부정 표면화는 경로 결함이라 고치고 다시 재서 값이 회복됐다. 다섯 사례에서 얻은 교훈("측정 도구도 검증 대상")이 여기서 두 칸 더 갔다 — **측정 대상 데이터도, 측정이 통과하는 경로도 검증 대상이다.** 그리고 이 정정들이 수치를 유리하게 바꾸지 않도록, 낮은 AUC를 성능 주장으로 재해석하지 않는다는 결정을 아래 ADR에 함께 박았다.

## 13.3 제약 — KPI 가드 3계층 (설계는 유효, 실행은 중단)

| 계층                | 성격                         | PR 차단   | 기준 형태        |

| B 운영 부하         | 큐 규모·실행시간·분포        | **HARD**  | 절대값 또는 ±50% |
| C truth 회귀 방지선 | 회귀 감지                    | SOFT WARN | 기준선 × 70%     |

성능 지표(C)만 SOFT인 것이 핵심이다. **truth recall 향상을 강제하는 가드를 두지 않는다** — 그런 가드가 있으면 결국 데이터에 맞춰 룰을 조정하게 되기 때문이다. 기준선 갱신 시에도 도메인 정당성을 명시해야 하고 recall 향상을 사유로 쓸 수 없다.

이 3계층 설계는 유효하고 문서·스크립트로 보존돼 있지만, **이를 실행하던 CI 워크플로는 2026-07-24에 제거됐다**([10장](10_PLATFORM.md) 10.6). 제거 사유 자체가 이 표의 한계를 가리킨다 — Layer B·C의 일부 항목이 등급 폐지로 사라진 축을 참조하고 있어 기준이 낡았고(재계산 미확인), 기준선이 스스로 "퇴역" 상태였고, 검사 대상 산출물이 CI 런너에 존재하지 않았다. **가드는 기준선이 살아 있을 때만 가드다.**

### 차단 근거 전수 재검의 재현 (2026-07-29)

```bash
  data/journal/primary/datasynth_semantic_v1_phase2_fraud_s10_20260727_r9
```

검증 설계가 요점이다. **분모를 손으로 만들지 않는다.**

```
  파이프라인 실행 ─▶ featured 98칸 ─┬─▶ population.txt (분모 박제)
                                    │
                                    └─▶ 칸마다 측정 ─▶ done.txt (흔적)
                                                          │
                              census_diff.py ◀────────────┘
                                    │
                                 PASS 98/98 → 완료 선언 가능
```

| 축                    | 측정                             | 판정 기준                          |
| --------------------- | -------------------------------- | ---------------------------------- |
| 수치형·불리언         | 단독 AUROC — 행 단위 · 문서 단위 | HARD ≥ 0.95 · SOFT 0.80~0.95       |
| 범주형                | 최고 단일 값의 정밀도·재현율     | HARD 정밀도 ≥ 0.99 & 재현율 ≥ 0.05 |
| 재측정 대상이 아닌 것 | —                                | 구조적차단(정답지·식별자·비식별화) |

기준선은 **v6 감사가 쓴 것을 그대로** 썼다. 재검하는 쪽이 기준을 새로 정하면 그 자체가 자의적이 되고, 완화하려는 방향으로 무의식적으로 기울 수 있다.

방향 무관 AUROC(`max(a, 1-a)`)를 쓴다 — 어느 쪽으로 갈리든 지름길이기 때문이다. 문서 단위는 전표별 합계로 집계해 행 단위와 함께 보고, **둘 중 큰 값**으로 판정한다. 한 축만 보면 `near_threshold_gap_ratio`(행 0.70 / 문서 0.86)처럼 판정이 뒤집힌다.

| 산출          | 경로                                                |
| ------------- | --------------------------------------------------- |
| 컬럼별 판정표 | `reports/s5_fraud_overlay/deny_basis_recheck_*.csv` |
| 분모·흔적     | `*_population.txt` · `*_done.txt`                   |

## 13.7 실증 예시 — 하나의 판정이 뒤집히는 과정

빌더 정확성 판정(S4)이 FAIL에서 exit 0이 되기까지를 따라간다.

판정 스크립트를 처음 돌렸을 때 V4(정답지 하한) 축에서 실패가 나왔다. 어휘 19룰 중 관계사 룰만 단독 선택했을 때 **자기 표적 문서가 하나도 매칭되지 않았다.** 룰은 분명히 발화하는데 빌더가 못 찾는 상황이었다.

추적해 보니 발화는 정상이었다. 문제는 그다음 단계였다. 빌더는 케이스 빌더가 만든 unit에서 증거를 읽는데, 그 수집 과정에 topic 게이트가 있다. 관계사 룰의 메타데이터가 **2026-06에 삭제된 topic을 여전히 참조**하고 있어서, 게이트를 통과하지 못하고 전량 탈락한 것이다.

원인은 이중 레지스트리의 편측 갱신이었다. 점수 레지스트리는 이 룰을 다른 topic으로 재배치했는데 메타데이터는 갱신되지 않았고, 하필 메타데이터가 우선 적용되는 구조였다. 등급 체계 시절에는 이 룰이 보조 신호라 증상이 드러나지 않았고, 조합 빌더의 몸통(감리 확정 80건)으로 승격되면서 비로소 보였다.

메타데이터의 topic을 올바른 값으로 고치자 **증거 보유 unit이 0에서 199로** 바뀌었고, 파급 테스트 179개가 통과했으며, 재판정에서 전 축이 통과해 exit 0이 나왔다.

이 사례가 검증 설계의 가치를 보여준다. "빌더가 정확한가"를 독립 재구현과 대조하지 않았다면, 관계사 조합은 조용히 항상 0건을 반환했을 것이다. 화면에는 아무 오류도 뜨지 않고, 감사인은 "이 회사엔 관계사 이슈가 없구나"라고 잘못 결론 냈을 것이다.
