# 11. 대시보드 — 현재 어디까지 만들어졌나

## 11.1 파이프라인 내 위치

```
생성 → 품질검증 → 수집·파생·검증 → 탐지 → 표면 → 적재 → ▶▶▶ [화면] ◀◀◀
```

**이 장은 미완성 구간을 기록한다.** 분석 엔진과 검증 체계는 완주했지만 화면은 아직 다듬어지지 않았고, 그 상태를 정확히 남기는 것이 이 장의 목적이다.

## 11.2 실제로 도달 가능한 화면 6개

`dashboard/app.py:274-311`이 import하고 호출하는 화면이 전부다(`dashboard/_state.py:63-70` `RESULT_PAGES` 6개).

```
[회사 선택/등록]  page_company.py
        ▼
[업로드 → 매핑 확인 → 파이프라인 실행]  components/data_uploader.py
        ▼
┌─────────────────── 결과 화면 (탭 6개) ───────────────────┐
│ 개요            tab_overview.py         1,157줄          │
│ 회사별 설정     app.py 내부 함수                          │
│ 룰 기반         tab_phase1.py           4,194줄  ★       │
│ 분석적 검토     tab_analytical.py         295줄          │
│ 전기 비교       tab_comparison.py       1,492줄          │
│ 비지도(VAE)     tab_phase2.py           4,112줄          │
└──────────────────────────────────────────────────────────┘
```

탭 라벨(`룰 기반` / `분석적 검토` / `비지도(VAE)`)이 곧 3-surface 불변식의 화면상 노출이다. 탭 전환은 nav만 담당하고 **활성 탭만 렌더**한다. 6개 패널을 동시에 평가하면 로딩이 느려지기 때문이다.

2026-07-25에 탭 구성을 두 번 손봤다. 먼저 `Phase1,2 비교` 탭(`tab_phase_comparison.py` 262줄)을 **삭제**했다 — 세 표면을 한 화면에서 맞대보는 구성이 3-surface 비병합 원칙과 어긋나는 방향이었고, 각 표면 탭이 자기 근거를 다 갖추면서 존재 이유가 사라졌다. 이어 `전기 비교`를 `비지도(VAE)` 앞으로 옮겼다. 전기 비교는 룰·분석적 검토와 같은 PHASE1 산출물을 전기와 맞대보는 화면이라 앞의 두 탭에서 흐름이 그대로 이어지고, 별도 실행이 필요한 PHASE2를 마지막에 두는 편이 실제 실행 순서와도 맞는다.

미배선 모듈에 딸린 컴포넌트도 함께 도달 불가 상태다. 탐색기 그리드, 전표 상세 패널, 예외처리 CRUD, SHAP 워터폴, 검토 큐 브라우저·워크플로가 여기 해당한다. 코드 자체는 완성돼 있고 테스트도 있지만 **화면에서 갈 수 있는 길이 없다.**

## 11.4 조합 빌더 패널 — 가장 최근에 만들어진 화면

PHASE1 탭의 `조합별 검토` 하위 탭이 조합 빌더를 호출한다(`components/phase1_combo_builder_panel.py`, 271줄).

| 요소      | 구현                                                                                                     |
| --------- | -------------------------------------------------------------------------------------------------------- |
| 프리셋    | **금감원 사례 조합 카드 5장** — 카드마다 `대상 논리식 / and / 수법 논리식` 3단 + "이 유형으로 검토" 버튼 |
| 어휘 선택 | **체크박스 표 2개**(`st.data_editor`) — "조작 대상" 10 / "조작 방법" 10, 접이식 `직접 조합` 안           |
| 엄격 모드 | **UI 미노출** — 엔진은 `strict` 인자를 유지하지만 패널이 넘기지 않아 화면은 기본 모드만 쓴다             |
| 결과      | AgGrid 표 — "발화 룰"·"배지" 라벨 컬럼, 표시 상한 200건(일치 건수는 절단 전 전체 수)                     |
| 드릴다운  | **구현됨** — 행을 클릭하면 그 전표(흐름이면 구성 전표 전부)의 실제 분개 라인이 아래에 펼쳐진다           |

프리셋의 표현이 이 화면의 설계 의도를 보여준다. 이전 판은 프리셋을 버튼 5개로 두고 몸통 라벨에 감리 건수(추정계정 147 …)를 붙여 "근거의 양"을 보여줬는데, 지금은 카드 본문에 **그 프리셋이 실제로 어떤 룰 논리식인지**를 그대로 적는다 — 예컨대 `(L3-10 추정계정 or L3-03 관계사)` **and** `(L1-04 승인한도초과 or L1-05 자기승인 or …)`. 추상 라벨을 없애고 결합 의미론(그룹 내 OR, 그룹 간 AND)을 화면에서 읽히게 만든 것이며, 시스템이 "이게 더 위험하다"고 말하지 않는다는 원칙은 그대로다. 감리 건수는 어휘 정본(`config/combo_builder.yaml`의 `fss_confirmed`)에 남아 있고 화면에는 노출하지 않는다.

드릴다운은 이 장의 이전 판이 "미구현"으로 적어 둔 항목인데 **구현됐다**. 그리드가 선택 이벤트를 소비해(`configure_selection`) 선택된 unit의 문서 ID로 원장 라인을 조회한다. 같은 그리드 함수(`render_unit_result_grid`)를 룰별 커버리지 큐가 `key_prefix`만 바꿔 재사용하므로, 두 표면의 드릴다운 동작이 갈리지 않는다. 세션에 원장 데이터가 없는 폴백 로드 상태에서는 "원장 데이터가 없어 표시할 수 없다"고 밝히고 빈 표를 그리지 않는다.

## 11.5 PHASE1 탭의 상태 — 4,194줄과 미검증

`tab_phase1.py`는 4,194줄이며 최상위 정의가 92개다. **3개** 하위 탭(전체 요약 / 데이터 정합성 / 조합별 검토)을 담고 있고 조합별 검토가 조합 빌더와 커버리지 큐를 호출한다. 구 `통계 결과` 탭은 case·priority_band 기반 차트라 등급 폐지와 함께 폐기했고, 모집단 프로파일은 전체 요약으로 이관했다.

**개별 함수의 동작은 전수 검증되지 않았다.** 등급 폐지 대수술 후 도달 불가 블록 310줄을 삭제했고 관련 테스트는 통과했지만, 92개 함수 각각이 의도대로 동작하는지는 확인되지 않았다. 이것이 "Streamlit을 아직 제대로 만들지 못했다"의 구체적 내용 중 하나다.

전체 요약의 **분석 룰 요약**(룰 오딧 패널)은 2026-07-25에 집계 결함 두 건을 고쳤다. 계정 단위 신호(L4-02·D01·D02)는 전표 case를 만들지 않으므로 전표 건수가 구조적으로 항상 0인데, 패널이 "건수 0이면 스킵됨"으로 강제 라벨링해 전기 데이터가 있는데도 실행되지 않은 것처럼 보였다. 지금은 계정 단위 신호는 건수 대신 판정 문구(`변화 확인` / `변화 없음`)로 표시하고, 실행 상태는 추정이 아니라 `detector_statuses`의 `run_status`로만 판정해 스킵 사유를 한글로 붙인다. 같은 이유로 L1-01·L1-02·L1-03은 case 묶음 없이 **전표 단위로 따로 센다** — case 기준으로 세면 실제 위반이 있어도 항상 0건이 되어 데이터 정합성 탭 상세와 어긋났다.

## 11.7 실증 예시 — 감사인이 지금 실제로 할 수 있는 일

현재 상태에서 데모가 어디까지 가는지 따라간다.

앱을 실행하면 **회사 선택** 화면이 뜬다. 회사를 만들거나 고르고, 감사연도를 선택하면 그 조합에 해당하는 DuckDB가 열린다(없으면 생성).

**업로드** 단계에서 원장 CSV를 넣으면 3단계 스테이지가 돈다: 업로드 → 매핑 확인 → 파이프라인 실행. 매핑 확인 화면에서 자동 매핑 결과와 애매한 후보가 나뉘어 표시되고, 감사인이 확정한다.

**실행**이 끝나면 결과 화면으로 전환된다. **개요** 탭에서 전체 규모와 KPI, Benford 요약을 본다. **룰 기반** 탭으로 가면 세 개 하위 탭이 있고, `조합별 검토` 탭에서 조합 빌더를 만난다.

여기서 "비용자산화" 카드의 `이 유형으로 검토`를 누르면 [7장](7_PHASE1-1_COMBO-BUILDER.md) 7.9절의 흐름이 그대로 화면에서 일어난다 — 몸통 1개·특징 10개가 체크되고, 일치 건수가 표시되고, 정렬된 목록이 "발화 룰" 컬럼과 함께 나온다. 감사인은 `직접 조합`을 펼쳐 체크박스로 조합을 바꾸면서 건수 변화를 보고 범위를 조절한다. 행을 클릭하면 그 전표의 실제 분개 라인이 표 아래에 펼쳐져, 목록에서 본 "발화 룰"이 어느 차변·대변 줄에서 나온 이야기인지까지 확인할 수 있다.

**분석적 검토** 탭은 PHASE1-2 전용 표면이며 하위 탭 3개(`Benford 분포` / `Round Number 밀집` / `거래처 신호`)로 나뉜다. 전표 한 장으론 안 보이고 계정·거래처를 모아야 드러나는 신호를 룰 큐와 **별도 큐**로 렌더한다. 이 분리가 3-surface 비병합의 화면상 구현 중 하나다.

세 하위 탭은 2026-07-25에 "표 대신 그 신호가 실제로 무엇을 말하는지"로 다시 짰다. Benford는 계정별 분리 분석을 건수 순이 아니라 **이탈도(MAD) 순위**로 바꾸고 표본 300건 이상 그룹만 순위 대상으로 삼았다(Nigrini 권장선. 탐지기 자체의 그룹 게이트 500건과는 다른 화면용 게이트이고, 미달 그룹은 기타로 뭉치지 않고 `표본부족`으로 표에 남긴다). Round Number 밀집은 비율·기준선·초과분을 눈으로 빼서 비교해야 하는 표를 **수평 막대 + 원장 기준선 수직 점선**으로 바꿨다 — 막대 길이가 그 그룹의 둥근 금액 비율이고 점선을 넘어간 폭이 곧 초과분이라, 정렬이 그대로 검토 우선순위가 된다(초과분 상위 20개만 그리고 전체는 접힌 표에). 거래처 신호는 판정 기준 범례와 신호별 필터를 붙였다.

같은 PHASE1-2 신호 중 **계정 활동 변동(D01)·결산월 집중 변동(D02)은 `전기 비교` 탭 안에서** 표시한다(2026-07-25). 둘은 전기 engagement 를 붙여야 계산되는 신호라 전제가 전기 비교와 같고, 묻는 질문도 같기 때문이다 — D01 은 `계정과목 변동` 소분류에서 변동액 Top 15(금액만 봄) 바로 아래에, D02 는 `분석적 절차(Flux)` 의 월별 추세(원장 전체) 바로 아래에 붙어 같은 축을 계정 단위로 이어 받는다. 표시 위치만 옮긴 것이고 신호 소유권과 점수 비병합은 그대로다.

이 이동은 화면 정리인 동시에 내용 교정이었다. 옮기기 전 표는 `가중변동 1.842`, `우선순위`, `버킷` 같은 **내부 점수만** 보여 감사인이 읽을 게 없었다. finding 안에는 금액·건수·평균의 당기/전기 원값이 이미 들어 있었는데 화면까지 오지 않았다.

**D01은 축을 감사인이 고른다.** 금액·건수·건당 금액 세 축을 한 표에 12열로 늘어놓으니 어느 숫자가 어느 축인지 읽히지 않았고, 정렬을 금액 하나로만 하니 "금액은 비슷한데 건수가 1/10"인 계정이 아래로 밀렸다. 세 축을 합성 점수로 묶는 길은 가중치 근거가 없어 이미 폐기한 방향이므로, 합치는 대신 `비교 축` 라디오(금액 / 건수 / 건당 금액)를 두고 고른 축의 네 열(전기·당기·변동·증감률)만 남긴다. 정렬도 그 축의 변동이다. 라디오가 페이지 전체를 다시 그리면 브라우저가 탭 상단으로 튕기므로 이 섹션만 `st.fragment`로 격리했다.

**D02는 한 문장으로 좁혔다.** 구 표는 "가장 몰린 달 11월 → 12월"처럼 달 이름 이동을 앞세우고 변화폭도 절대값이라, 결산월로 쏠린 계정과 쏠림이 풀린 계정이 같은 값으로 뒤섞이고 7월 몰림과 결산월 몰림을 구분하지 않았다. 감사에서 읽고 싶은 문장은 **"이 계정, 연간 금액 중 결산월분이 전기 9% → 당기 38%"** 하나이므로 그 축만 남겼다 — 결산월 비중(전기/당기)·증가분(%p)·당기 거래 금액. 증가분은 부호를 유지해 증가가 위로 온다. 결산월은 12월로 박지 않고 그 원장에서 관측된 최대 회계기간으로 정한다(3월·6월 결산 법인에서 조용히 틀리지 않게). 결산월 비중은 2026-07-25에 추가된 진단값이라 그 전에 실행해 둔 결과에는 없는데, 이 탭은 이미 전기 DB를 붙여 SQL을 돌리므로 값이 없으면 계정×월 활동금액을 다시 집계해 **백엔드 D02 함수를 그대로 호출**해 채운다. 2년치를 30분 재실행하게 만들지 않으면서 판정식은 한 곳에만 둔다.

**임계는 전부 걷어냈다.** 두 신호에는 목록을 자르는 컷이 있었다 — D01은 가중변동 0.5(가중치도 0.5/0.3/0.2), D02는 JSD 0.3·비중변화 0.25·전표 100건. 어느 숫자도 근거를 댈 수 없었고, 그 결과 실제 데이터에서 D02는 계정 하나만 남아 화면이 고장 난 것처럼 보였다. 지금은 **자르지 않고 전부 세운 뒤 정렬로만 우선순위를 표현한다.** 둘 다 표에 이미 보이는 숫자가 그대로 정렬 키라, "왜 이 계정이 맨 위인가"를 표 안에서 확인할 수 있다. 유일하게 목록에서 빠지는 건 거래한 달이 한두 달뿐이라 분포를 비교할 수 없는 계정이고, 그건 신호 강도 컷이 아니라 계산이 성립하지 않는 경우다.

임계를 없애면서 **D01·D02가 전표에 달던 꼬리표도 함께 뗐다**(`account_activity_shift`·`ratio_variance_account` 배지와 case의 macro_context). 꼬리표를 달려면 "어느 계정부터 꼬리표인가"를 가르는 임계가 필요한데 그 임계를 버렸고, 임계 없이 전 계정에 달면 꼬리표가 아무것도 구분하지 못한다. 두 신호는 이제 계정 단위 순위 목록으로만 쓰인다.

**비지도(VAE)** 탭에서 VAE 결과를 별도로 볼 수 있다. 점수가 PHASE1과 합쳐지지 않고 따로 표시되는 것이 3-surface 비병합의 나머지 한 축이다. 이 탭도 2026-07-25에 정리했다. 하위 탭과 실행 요약 KPI·분석 영역 요약을 걷어내고 **score 분포 차트 + 요약 카드**를 바로 띄운 뒤 그 아래에 전표 상세 목록을 이어 붙였고, 용어를 `case`에서 `전표`로 통일했다. 새로 붙인 것은 **ROC 곡선**이다(좌 곡선 / 우 AUC·부정 전표·평가 전표·부정 비율 카드). VAE는 학습에 라벨을 쓰지 않고 이 곡선은 평가 전용이라는 점을 화면에도 적어 둔다.

ROC를 붙이는 과정에서 정책 충돌이 하나 드러났다. 파이프라인은 라벨이 피처로 새는 것을 막기 위해 `is_fraud`를 초입에서 제거하므로(9장 3차 방어), fraud 데이터셋을 넣어도 DB에는 라벨이 없다 — 실측으로 `general_ledger` 238,672행의 `is_fraud`가 전부 NULL이었다. 학습 경로를 건드리지 않고 **원본 DataSynth CSV의 문서 단위 라벨만 평가 전용으로 따로 읽는** 해소기를 두어 풀었다(`components/phase2_roc_truth.py`). 라벨은 그 함수 밖으로 나가지 않으므로 피처·점수에는 여전히 참여하지 않는다. 라벨을 못 찾으면 곡선 대신 사유를 적는다 — "부정 라벨이 없다"와 "원본 파일을 못 찾았다"와 "document_id가 맞물리지 않는다"를 각각 다른 문장으로 구분한다.

같은 라운드에서 이 탭의 더 큰 결함도 고쳤다. Phase 2 결과는 디스크에 저장되는데(`phase2_cases/<batch_id>/`) **앱 어디에서도 그것을 읽는 배선이 없었다.** 그래서 재시작·세션 초기화 후에는 case 3,368건이 디스크에 그대로 있는데도 화면이 "분석할 전표가 없다"고 말하고 학습·추론 10분을 다시 요구했다. 저장된 배치를 불러올 때 overlay와 같은 자리에서 case set도 붙이고, 화면 쪽 해소기도 세션 → 디스크 순으로 찾도록 배선했다. 실측으로 세션이 빈 상태에서 저장본만으로 unsupervised 3,368 + timeseries 173건을 복원하고 ROC까지 그렸다 — Phase 2 재실행 0회. **저장 배선과 로드 배선은 같은 변경에서 함께 넣어야 한다**는 것이 이 사고의 교훈이고, 로더 단위 테스트가 있었는데도 "앱이 실제로 부르는가"는 아무도 보지 않았다.

> 이 복원 확인에서 화면에 뜬 숫자(평가 전표 3,368건 중 부정 47건, AUC 0.660)는 **배선이 동작한다는 증거일 뿐 성능 수치가 아니다.** 같은 계열에서 시드 4벌을 문서 단위로 채점한 값도 학습 5만 행 0.5187, 20만 행 1.0000으로 뒤집혔고, **세 수치 모두 구 overlay·구 입력 시절의 값이라 인용하지 않는다.** 인용 가능한 값은 되돌아오는 흐름을 채운 base의 시드 4벌 평균 문서 AUROC **0.8445** 하나다([9.6](9_PHASE2_VAE.md)). 화면에도 "평가 전용" 표기를 붙였다.
>
> 이 0.660이 진단의 출발점이었다. "왜 이 숫자가 낮은가"를 파다가 데이터에 결측 지름길 16개가 있다는 것이 나왔다 — 화면에 지표를 띄운 것이 데이터 결함을 잡은 셈이다. 감추지 않고 그린 값이 자기 데이터를 심문하게 만든 사례로 남긴다.

여기까지가 현재 동작하는 범위다. 룰 기반·분석적 검토·비지도(VAE) 세 표면은 화면에서 각각 도달 가능하다. 다만 검토 큐에 판정을 기록하거나, 결과를 Excel로 내보내는 것은 **코드는 있으나 화면에서 갈 수 없다.** 데모로 보여줄 수 있는 것과 제품으로 쓸 수 있는 것 사이의 거리가 여기 있다.
